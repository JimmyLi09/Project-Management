# 需求：用户管理 —— 按角色的权限表 + 删除用户（先转交再删）

- **需求编号**：REQ-051
- **所属系统**：Project-Management（项目协作台 · 用户管理）
- **状态**：已确认
- **创建日期**：2026-10-12
- **优先级**：P1 · 1009 批次
- **来源**：
  - `Progress comments - 0924.docx`（1009 版）第 5 条「需要增加权限设置，同时需要可以删除用户的功能。只有 PD、BD 可以操作」；
  - 1009 选定：按角色的权限表、先转交再删；
  - 原型 v2 →「用户与权限」，1012 确认。
- **关联**：REQ-043（PM / Engineer 只看自己的项目）。

## 1. 现状（查代码确认）
- 权限全部**写死在代码里**，按角色判断（`permissions.ts`：`canEdit`、`canAssign`、`canDelete`、`canAdmin`、`canViewPrices`…约 50 个函数），界面上改不了。
- 只能「停用」账号（`api/users/route.ts:91-99`，不能停用自己和最后一个 PD / BD），没有删除。停用存在两个问题：
  - 只在登录时检查（`auth/login/route.ts:35`）；已登录的会话不检查 `disabled`（`session.ts:59-64`），停用后仍能继续用；
  - 各处指派下拉没有排除停用的人（`ScheduleTab.tsx:45`、`ChecklistTab.tsx:56`、`ProjectsView.tsx:446,449`、`ProjectDetail.tsx:259,844`）。
- 项目里引用用户都是**按名字**：owners、perm、engineer、`pk.owner`、排期 assignee、清单 owner、收料 by / receivedBy、日志 by、交接 / 完工 / 开票的操作人…
  - 改名同步 `propagateRename`（`db.ts:975-987`）只覆盖其中 5 种。

## 2. 功能说明

### 2.1 权限设置（按角色的权限表）
- 「用户与权限」新增「权限设置」标签：
  - 行是功能模块：项目列表、项目档案 / Job Record、信息清单、排期、财务 / 开票、AV 方案成本、通讯录、统计报表、用户与权限（开发可以按实际模块细分，但不要多于 15 行）；
  - 列是角色：PD / BD / Sales / PM / Engineer / Finance；
  - 每格选「不可见 / 只读 / 可编辑」。
- **默认值 = 现在代码里的规则**。上线后行为不变，PD / BD 想改再改。
- PD / BD 两列锁定为全部可编辑，避免把自己锁在外面。
- REQ-043（PM / Engineer 只看自己的项目）继续叠加生效：权限表决定「能不能做」，REQ-043 决定「对哪些项目」。
- **实现方式**：
  - 现有 `permissions.ts` 的函数改为先查权限表（存数据库，带默认值），再叠加原有的业务规则（比如「Finance 才能改开票信息」这类细则保留在代码里，权限表只控制模块级的可见 / 可编辑）；
  - **后端接口同样校验**，不只是前端隐藏。
- 保存后已登录的人刷新即生效。每次修改写日志：谁、何时、把哪个角色的哪个模块从什么改成什么。

### 2.2 删除用户（先转交再删）
- 只有 PD / BD 能删除；PD / BD 账号本身不能删；至少保留 1 个 PD。
- 删除弹窗显示他名下的工作：负责的项目数、未完成待办数、指派的信息清单项数。每类选一个接手人（默认同角色的第一个人），然后勾「我确认删除」。
- 删除时的处理：
  - 他的 owners / engineer / perm / 服务包负责人 / 排期负责人 / 清单负责人全部替换为接手人，写日志「X 的工作转交给 Y」；
  - 账号标记为已删除：不能登录，**已登录的会话立即失效**；用户列表、通讯录内部人员、各种指派下拉都不再出现；
  - **历史记录保留原名**：收料记录、日志、交接 / 完工 / 开票操作人都不改，显示「X（已删除）」。
- 「停用」功能保留，修两个问题：会话也要检查停用状态；各指派下拉排除停用和已删除的人。
- 顺便把 `propagateRename` 补全，覆盖所有按名字引用的地方。

## 3. 验收标准
- [ ] 以 PD 登录：权限表默认值和现在的行为一致；把 Engineer 的「排期」改成「不可见」→ Engineer 刷新后看不到排期标签，直接调接口也被拒绝。
- [ ] 以 PM 登录：看不到「用户与权限」，接口也拒绝。
- [ ] 删除 Marcus（有 2 个项目、4 项待办）→ 必须选接手人；删除后这些项目和待办都在接手人名下，Marcus 不能登录，已打开的页面下一次请求即退出；历史日志仍显示「Marcus（已删除）」。
- [ ] 不能删除 PD / BD，也不能删除最后一个 PD。
- [ ] 停用的账号已登录会话立即失效；指派下拉里看不到停用和已删除的人。
- [ ] 所有新文案中英两套。

## 4. 落地说明

- **权限表**（`src/lib/permTable.ts`，存在 meta 表 `perm.table`；没存过 = 默认）
  - 9 行：项目列表、项目档案 / Job Record、信息清单、排期、财务 / 开票、AV 方案成本、通讯录、统计报表、用户与权限。原型把「项目档案」和「Job Record」分成两行，代码里它们读写的是同一份资料，分开设会互相矛盾，所以合成一行。
  - 列：PD / BD（锁定可编辑）/ Sales / PM / Engineer（系统角色名「成员」）/ Finance。「只读」角色不进表，照旧全部只读。
  - **表是上限**：每格的默认值 = 这个角色在上线前的代码里最多能做到的程度，所以上线后行为一点不变（单元测试把 14 个权限函数在 7 个角色 × 4 种人身上逐一和旧写法对比过）。
  - 每格的选项只到这个上限为止，比如 PM 的「财务 / 开票」只能选「不可见 / 只读」，因为原来 PM 就改不了开票。想让某个人改某个项目，照旧在项目里给他「编辑授权」。「项目列表」至少只读，否则其它页面都打不开。
  - 原型里的默认值（比如 Engineer 的排期只读、Finance 的信息清单不可见）是示意；按本文「默认值 = 现在代码里的规则」走。PD / BD 想按原型来，在表里改了保存即可。
  - 原有细则照旧叠加在表上：只有 Finance 能改开票信息、Sales 要有项目「编辑授权」才能改制作内容、REQ-043 PM / Engineer 只看自己的项目……
- **后端同样校验**
  - 项目的每个写操作先查这个动作属于哪个模块（`ACTION_MODULE`），模块不是「可编辑」就拒绝（403，中英文提示），再走原来每个动作自己的规则。指派 PM / 工程师、转交、归档、积分、决策、审批本来就只有 PD / BD 能做，不过表。
  - 项目接口（列表、单个、改完返回的、复制、导入片段、立项）对「不可见」的模块不下发内容：
    - 排期只留状态、日期、负责人（项目进度和「谁在这个项目上」照样算得出），任务名和备注清空；
    - 信息清单、Job Record、联系人、开票信息整块清空；
    - 项目日志里属于这些模块的条目一起拿掉（老日志没有分类，原样保留）。
  - AV 方案成本「不可见」时，`/api/av/*` 全部拒绝。导入排期 / 清单片段也先过表。
  - 「用户与权限」的接口（建 / 改 / 删账号、改权限表、看管理日志、看某人名下的工作）只有 PD / BD。
  - 前端：侧栏不显示「不可见」的页面，直接打网址进来只看到「没有权限」；项目详情不显示对应标签；排期不可见时「我的待办」和铃铛里也没有排期任务。
  - 权限表随首屏下发，之后每 30 秒和项目一起刷新。所以 PD 保存后，别人刷新页面即生效（最多 30 秒也会自动生效）。
  - 每改一格写一条管理日志（新表 `admin_log`），在「权限设置」下面的「修改记录」里看：谁、何时、哪个角色哪个模块、从什么改成什么。
- **删除用户（先转交再删）**
  - 账号页每行多两列「负责项目」「未完成待办」，非 PD / BD、非自己的账号有「删除」。
  - 弹窗从服务端取他名下的工作：负责的项目数、未完成待办数、指派的信息清单项数。每类选接手人：同角色的排前面，默认第一个；候选里没有停用的人。勾「我确认删除」后才能点「转交并删除」。
  - 转交范围：
    - 项目职责（PM、工程师、编辑授权、服务包负责人、还没接单的交接）给「项目」的接手人；
    - 没完成的排期行给「待办」的接手人；
    - 没确认的清单项给「信息清单」的接手人。
    - 已完成的排期、已确认的清单项、已归档的项目是历史，保留原名。
  - 每个受影响的项目写一条日志「X 的工作转交给 Y（删除账号，共 N 处）」，另写一条管理日志。
  - 账号行不删，打上 `deleted_at` 并停用：
    - 不能登录（提示「账号已删除」）；
    - 已登录的会话下一次请求就失效，已打开的页面下一次操作或下一次刷新数据就回到登录页；
    - 用户列表、团队负载、各种指派下拉都不再出现；
    - 历史记录（日志、收料记录的接收人、交接 / 完工 / 核对 / 开票的操作人、已完成行的负责人）显示「X（已删除）」。
  - 删除前先转交、转交加标记删除在一个事务里，要么都成要么都不成。
  - 规则：PD / BD 账号不能删（所以永远至少有 1 个 PD），也不能删自己。最后一个可用的 PD 不能停用、不能降级。已删除的人的姓名和账号名不能被新账号复用：历史记录按姓名认人，复用了就分不清是谁。
- **停用**
  - 保留原样，修了两点：
    - 会话每次请求都查停用 / 删除状态（`session.ts`），停用即时生效；
    - 前端的 `users` 只含可用账号，所以所有指派下拉（排期、信息清单、PM、工程师、交接、转交）和团队负载自动排除停用和已删除的人。KPI 看板是绩效记录，停用的人照旧显示，已删除的不再出现。
  - 「最后一个 PD / BD」的计数只数可用账号。
  - 停用 / 恢复写管理日志。
- **改名同步补全**（`src/lib/peopleRefs.ts`，一个事务）
  - 以前覆盖 owners、perm、engineer、服务包负责人、排期 assignee。现在还包括信息清单负责人（含迁移前备份和已移除的项）、交接给谁，以及培训的指派、进度和成绩。
  - 日志、收料记录这类「当时是谁做的」不改。
- **数据库**：都是增量变更，启动时自动完成，不改不删旧数据。
  - users 加一列 `deleted_at`（默认 0）。
  - 新表 `admin_log`。
  - meta 的 `perm.table` 只在 PD / BD 保存权限表时才写。
  - 新代码在 REQ-052 时代的旧库上启动实测过：自动加列、加表，用户和项目数不变。
- **回退**：`scripts\req051-rollback.bat`。
  - 退回旧代码**不需要跑任何东西**：旧代码不认新列、新表、新 key；被删除的账号在旧版本里显示「已停用」，同样登录不了。
  - 脚本不带参数只报告；`--reset-perms` 把权限表恢复默认；`--undelete <账号>` 撤销误删（账号仍停用，转交出去的工作不自动转回，项目日志里有记录）。写库前先备份，并出报告。
- **已知边界**
  - 「统计报表」设为不可见只是藏页面：统计是用他本来就看得到的项目数据在浏览器里算的。
  - 删除用户只转交未归档项目上的工作。
- **测试**
  - 单元测试 9 个：
    - 默认表下 14 个权限函数与旧写法逐一相同；
    - 默认表下上线前能做的动作照样能做；
    - 上限、下限和坏值的处理；
    - Engineer 排期不可见时动作被拒、下发内容清空；
    - 模块只读；
    - 动作和模块的对照；
    - 转交（历史保留、归档不动、不写空名字）；
    - 改名补全。
  - 端到端 58 项，对照第 3 节逐条验收，加英文界面和恢复默认。
  - 回归：REQ-046/047、AV-016/017/019 的端到端全部通过。
