# 需求：用户管理 —— 按角色的权限表 + 删除用户（先转交再删）

- **需求编号**：REQ-051
- **所属系统**：Project-Management（项目协作台 · 用户管理）
- **状态**：已确认
- **创建日期**：2026-10-12
- **优先级**：P1 · 1009 批次
- **来源**：
  - `Progress comments - 0924.docx`（1009 版）第 5 条「需要增加权限设置，同时需要可以删除用户的功能。只有 PD、BD 可以操作」；
  - 1009 选定：按角色的权限表、先转交再删；
  - 原型 v2 →「用户与权限」，1012 确认。
- **关联**：REQ-043（PM / Engineer 只看自己的项目）。

## 1. 现状（查代码确认）
- 权限全部**写死在代码里**，按角色判断（`permissions.ts`：`canEdit`、`canAssign`、`canDelete`、`canAdmin`、`canViewPrices`…约 50 个函数），界面上改不了。
- 只能「停用」账号（`api/users/route.ts:91-99`，不能停用自己和最后一个 PD / BD），没有删除。停用存在两个问题：
  - 只在登录时检查（`auth/login/route.ts:35`）；已登录的会话不检查 `disabled`（`session.ts:59-64`），停用后仍能继续用；
  - 各处指派下拉没有排除停用的人（`ScheduleTab.tsx:45`、`ChecklistTab.tsx:56`、`ProjectsView.tsx:446,449`、`ProjectDetail.tsx:259,844`）。
- 项目里引用用户都是**按名字**：owners、perm、engineer、`pk.owner`、排期 assignee、清单 owner、收料 by / receivedBy、日志 by、交接 / 完工 / 开票的操作人…
  - 改名同步 `propagateRename`（`db.ts:975-987`）只覆盖其中 5 种。

## 2. 功能说明

### 2.1 权限设置（按角色的权限表）
- 「用户与权限」新增「权限设置」标签：
  - 行是功能模块：项目列表、项目档案 / Job Record、信息清单、排期、财务 / 开票、AV 方案成本、通讯录、统计报表、用户与权限（开发可以按实际模块细分，但不要多于 15 行）；
  - 列是角色：PD / BD / Sales / PM / Engineer / Finance；
  - 每格选「不可见 / 只读 / 可编辑」。
- **默认值 = 现在代码里的规则**。上线后行为不变，PD / BD 想改再改。
- PD / BD 两列锁定为全部可编辑，避免把自己锁在外面。
- REQ-043（PM / Engineer 只看自己的项目）继续叠加生效：权限表决定「能不能做」，REQ-043 决定「对哪些项目」。
- **实现方式**：
  - 现有 `permissions.ts` 的函数改为先查权限表（存数据库，带默认值），再叠加原有的业务规则（比如「Finance 才能改开票信息」这类细则保留在代码里，权限表只控制模块级的可见 / 可编辑）；
  - **后端接口同样校验**，不只是前端隐藏。
- 保存后已登录的人刷新即生效。每次修改写日志：谁、何时、把哪个角色的哪个模块从什么改成什么。

### 2.2 删除用户（先转交再删）
- 只有 PD / BD 能删除；PD / BD 账号本身不能删；至少保留 1 个 PD。
- 删除弹窗显示他名下的工作：负责的项目数、未完成待办数、指派的信息清单项数。每类选一个接手人（默认同角色的第一个人），然后勾「我确认删除」。
- 删除时的处理：
  - 他的 owners / engineer / perm / 服务包负责人 / 排期负责人 / 清单负责人全部替换为接手人，写日志「X 的工作转交给 Y」；
  - 账号标记为已删除：不能登录，**已登录的会话立即失效**；用户列表、通讯录内部人员、各种指派下拉都不再出现；
  - **历史记录保留原名**：收料记录、日志、交接 / 完工 / 开票操作人都不改，显示「X（已删除）」。
- 「停用」功能保留，修两个问题：会话也要检查停用状态；各指派下拉排除停用和已删除的人。
- 顺便把 `propagateRename` 补全，覆盖所有按名字引用的地方。
