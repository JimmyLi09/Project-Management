# 需求：Job Record 按硬件 / 软件分开——硬件回到登记表，软件保留 4 栏

- **需求编号**：REQ-053
- **所属系统**：Project-Management（项目协作台 · Job Record / 项目档案）
- **状态**：已实现（#103，2026-10-12；落地说明见 §4）
- **创建日期**：2026-10-12
- **优先级**：P1 · 1012 上线后反馈
- **来源**：
  - JM 1012 上线检查：「关于 Job Record，硬件：LED、投影等，需要保留旧字段的方式。软件，部分现在新的格式是对的」；
  - 1012 选定：
    - 硬件 = LED、投影、TV、MAXHUB、灯箱、AV、弱电、光伏、3D VR/720；
    - 硬件显示「登记表 + 可选额外 4 栏行」；
    - 迁移拆出来的行直接删掉；
  - 原型 `Audax_JobRecord与售前接洽_原型_v2.html` →「项目详情 · Job Record」「上线迁移预览」「登记表管理」，JM 1012 确认；
  - 待确认 5 项：全部选第一项。
- **关联**：REQ-049（Job Record 4 栏）。本需求是对 REQ-049 的修正：软件部分不变，硬件部分回退。

## 1. 现状（查代码确认）
- REQ-049 之后，Job Record 是一张 4 栏表（`p.jobRecord`，`lib/jobRecord.ts`），所有业务都按 4 栏显示。
- 硬件原来的登记表（`pk.record`，字段定义在 `records.ts:98-232` 和 `record_fields` 覆盖）只在下方「旧字段（只读）」里显示，不能改。
- 上线迁移（`lib/mig049.ts`）把有值的登记表字段一个字段转成一行，硬件项目因此出现大量重复行。按 10/12 迁移副本统计：
  - 69 行拆出来的行：143 有 28 行、148 有 12 行、146 有 11 行、004 有 9 行、132 有 5 行、084 有 4 行；
  - 26 行只预填了业务名的空行。
- 内置登记表只有 7 张：scale / projector / led / vrar / maxhub / av / others。TV、灯箱、弱电、光伏没有登记表。
- LED 登记表的 `dimH` 字段标签是「Width 宽 (mm)」，但它其实是屏幕高度，参与 `sqm = dimL * dimH / 1e6` 计算。143 LED ② 就因此误填成 304，实际应为 3040。

## 2. 功能说明

### 2.1 业务分成硬件 / 软件
- 每种业务有一个「Job Record 格式」：
  - **硬件 · 登记表**：Job Record 显示登记表卡片；
  - **软件 · 4 栏**：保持 REQ-049 的 4 栏表。
- 默认硬件：`led`、`projector`、`tv`、`maxhub`、`lightbox`、`av`、`elv`、`pv`、`vrar`。其余都是软件，包括 cgi、ani、scale、drone、website、matterport、saleskit、unitmodel、brochure、video、interior、renovation、others。
- PD / BD 可以在「登记表管理」里改某个业务的分类。存数据库，默认值如上。
- **改分类不删数据**：`pk.record` 和 `p.jobRecord` 两种数据都保留，只是换一种显示方式。

### 2.2 硬件：登记表卡片（可编辑）
- 每份硬件服务包一张卡。同类两份分开显示，例如「LED ①」「LED ②」，有实例名时用实例名。
- 卡片内容和上线前项目里的「资料」卡一致：
  - 字段按组显示，**可以直接编辑**，写回 `pk.record`；
  - 公式字段（ƒ）自动计算；
  - 有状态下拉，底部显示「最后更新」。
- 权限沿用现在登记表的规则，REQ-043 和 REQ-051 的权限表不变。
- 每张卡下面有「**额外项目**（4 栏 · 可选）」：
  - 「＋ 加一行」，行格式是 Service Item / Detail / Quantity / Special Notes；
  - 用来记报价单上登记表没有的项目（安装、运输、保养…）。
- 额外行存在 `p.jobRecord`，每行多一个 `pk` 字段，记它属于哪一份服务包。
- **硬件可以一行额外项目都没有**。「每个业务至少保留一行」只对软件生效。
- 在额外项目区域粘贴 Excel 的 4 栏，和软件表一样按行追加。

### 2.3 新建 / 补齐硬件登记表字段
- **TV**：用 MAXHUB 那套字段。Address、Main Con、End User、Type / Size、Quantity、Installation、Signed Off、Remarks。
- **灯箱 lightbox**：

  | 字段 | 类型 |
  |---|---|
  | Address 地址 | 文本，必填 |
  | Main Con | 文本 |
  | Size 尺寸 (W×H mm) | 文本 |
  | Quantity 数量 | 文本 |
  | 画面材料 Print Material | 文本 |
  | 灯光 Lighting | 下拉：LED 背光 / 侧光 / 不发光 |
  | Installation 安装日期 | 日期 |
  | Signed Off 签收 | 日期 |
  | Remarks 备注 | 多行文本 |

- **弱电 elv、光伏 pv**：先用 AV 那套字段。
- 这些都是内置默认值，PD / BD 可以在登记表管理里覆盖，和现在 `record_fields` 的方式一样。
- 新登记表的 `kind` 都是 `install`，状态走安装类状态。

### 2.4 LED 两个小改动
1. **改名**：`dimH` 的标签从「Width 宽 (mm)」改为「**Height 高 (mm)**」，英文「Height (mm)」。key 不变，公式不变。导出 CSV 的表头同步改。
2. **尺寸自检**：
   - 计算每块箱体尺寸：长 ÷ 数量 L、高 ÷ 数量 H。
   - 结果不在常见箱体尺寸里时，卡片里出现黄色提示。常见尺寸：160 / 192 / 240 / 250 / 256 / 320 / 384 / 480 / 500 / 512 / 576 / 640 / 768 / 960 / 1000 mm，误差 ±1。
   - 如果把值 ×10 或 ÷10 后就对得上，提示里给出建议值和「改成 XXXX」按钮。
   - 「没错，忽略」后，这份服务包不再提示。记在 `pk.record.dimCheckIgnored`。
   - 示例：143 LED ② 高 304 ÷ 19 = 16 mm → 提示「是不是 3040？」。
   - 常见尺寸列表放在常量里，方便以后加。

### 2.5 软件：4 栏表不变
- REQ-049 的 4 栏表、粘贴、导入导出全部保留。只是不再显示硬件业务的分组。
- 页面顺序：上面「软件 · 制作类」4 栏表，下面「硬件 · 安装类」登记表卡片。项目只有一类时只显示那一块。

### 2.6 导出 / 导入 / 项目档案
- **Job Record CSV 导出**：一份文件包含三部分：
  - 软件 4 栏行；
  - 硬件登记表字段，每份一组，按字段名 / 值；
  - 硬件额外行。
- **项目档案（跨项目页）**：
  - 硬件业务的页签照旧读登记表，TV / 灯箱 / 弱电 / 光伏现在也有页签；
  - 软件业务读 4 栏表。
- **登记表导入**：硬件按登记表字段导入，软件按 4 栏导入。REQ-049 已经去掉的「必须是内置业务」限制保持去掉。

### 2.7 上线迁移（自动，可回退）
- 只处理**硬件业务**的 `p.jobRecord` 行。
- **删除**以下两类行：
  - 迁移写进去、之后没人改过的行：Detail = 登记表字段名（可带「LED ② · 」这类前缀），且 Quantity / Special Notes 的值 = 该份 `pk.record` 现在的值（下拉字段比显示名）；
  - 只预填了业务名、其余三栏都空的行。
- **不删**：上线后有人改过或新加的硬件行。原样转成那一份服务包的「额外项目」（补上 `pk`），并在报告里单独列出给 PD 看。
- 软件业务的行一行不动。
- 流程：
  1. 先给 `scripts\req053-dryrun.bat` 预演出报告，**JM 确认后**才跑正式迁移。**顺序必须是先预演、再正式**——050 那次是正式迁移 3 秒后才跑的预演，预演显示 0。
  2. 正式迁移前整库备份到 `data\backups\pre-req053-<时间>.db`。
  3. 删除的行原样存进项目的 `jobRecordLegacy053`。
  4. 报告写到 `data\migrations\053-jobrecord-<时间>.md`。
  5. 提供 `scripts\req053-rollback.bat`：不带参数只报告；`--apply` 才写库，写之前先备份。
- `pk.record` 一个字段都不动。
- 这次迁移**不改 143 LED ② 的 3040**，由 PD 在页面上点尺寸自检的「改成 3040」，这样留有操作日志。

## 4. 落地说明

- **业务分类**（`lib/jobFormat.ts`）：
  - 默认硬件：`led`、`projector`、`tv`、`maxhub`、`lightbox`、`av`、`elv`、`pv`、`vrar`；其余都是软件。
  - PD / BD 在「项目档案 → 登记表管理」里每种业务点「硬件 · 登记表」或「软件 · 4 栏」。存在 meta 的 `job.formats`，只存和默认不一样的那几项；改回默认就从里面去掉。
  - 改分类写管理日志（「用户与权限 → 权限设置」下面的修改记录）。服务端 2 秒内生效，不用重启。
  - 改分类**不动数据**：`pk.record` 和 `p.jobRecord` 两种都留着，只换显示方式。
    - 软件改成硬件：原来的 4 栏行显示在那张登记表卡的「额外项目」里；
    - 硬件改成软件：登记表字段在 4 栏表下面的「旧字段（只读）」里看得到。
  - 改分类的接口 `PUT /api/job-formats` 只有 PD / BD 能用；读（`GET`）登录了就能读。
- **Job Record 页**（`JobRecordTab.tsx`）：
  - 顺序：项目信息 → 「软件 · 制作类」4 栏表 → 「硬件 · 安装类」登记表卡 → 这个项目的业务。项目只有一类就只显示那一块。
  - **硬件卡**：每份服务包一张，同类两份是「LED ①」「LED ②」，有实例名用实例名。
    - 字段按组排，和上线前「资料」卡一样，直接在卡上改：文字 / 数字失焦保存，下拉 / 日期选了就存。
    - 公式字段（ƒ）跟着输入实时重算。
    - 卡头有状态下拉（安装类 / 交付类状态），PD / BD 有「增减字段」；底部是「最后更新」。必填没填的标「资料不完整」。
    - 这项业务一个字段都没有时，卡上写「还没有字段，需要先建」，PD / BD 有「＋ 建字段」按钮。
  - **额外项目**：每张卡下面一块 4 栏表（Service Item / Detail / Quantity / Special Notes），可以一行都没有。
    - 存在 `p.jobRecord`，每行多一个 `pk`，记它属于哪一份服务包。
    - 「＋ 加一行」，Service Item 预填业务英文名；可以删到 0 行。
    - 在这块上 Ctrl+V 粘贴 Excel 的几栏：按行追加到**这一份**，跳过表头，不按 Service Item 去认业务。
    - 删掉一份服务包时，它的额外项目不删：同类还有别的份，就归到第一份那张卡下；一份都不剩了，就显示在 4 栏表的「项目里已没有这项业务」组里。
  - **软件 4 栏表**和 REQ-049 一样（粘贴、导入导出都不变），只是不再显示硬件业务的分组。「每个业务至少保留一行」只对软件生效，服务端也只对软件拦。
  - 新建项目、加业务时，只有软件业务会加 1 行预填行；硬件业务不加。
- **新登记表**（`records.ts`，都是 `kind: install`，状态走安装类）：
  - TV：用 MAXHUB 那套 8 个字段。
  - 灯箱：按 §2.3 的 9 个字段，灯光下拉是 LED 背光 / 侧光 / 不发光。
  - 弱电、光伏：先用 AV 那套字段。
  - 都是内置默认值，PD / BD 可以在「增减字段」里覆盖，和现在的 `record_fields` 一样。
- **LED**：
  - `dimH` 的标签改成「Height 高 (mm)」/「Height (mm)」。key 和公式不变。
  - PD 以前在「增减字段」里存过 LED 那一套的，覆盖表里还是旧名：上线迁移时只把这一格改名，原来那份存在 meta 的 `mig.req053.ledFieldsPrev`。
  - **尺寸自检**：每块箱体 = 长 ÷ 数量 L、高 ÷ 数量 H。
    - 不在常见尺寸里（`LED_MODULE_SIZES`：160 / 192 / 240 / 250 / 256 / 320 / 384 / 480 / 500 / 512 / 576 / 640 / 768 / 960 / 1000 mm，误差 ±1）时，卡上出黄色提示。
    - 把值 ×10 或 ÷10 后对得上的，给出「是不是 XXXX？」和「改成 XXXX」按钮。
    - 「没错，忽略」记在 `pk.record.dimCheckIgnored`，这一份以后不再提示。
    - 两个按钮都写项目日志，例如「登记表尺寸自检：LED · #2「Height 高 (mm)」304 → 3040」。
- **下载**（`JobRecordExport.tsx`）：
  - 打印 / PDF：先软件 4 栏表，再每份硬件一组「字段名 / 值」，下面是它的额外项目。
  - CSV 一份文件三部分：软件 4 栏行 / 硬件登记表字段（每份一组，含状态，下拉写选项名、公式写算出来的值）/ 硬件额外行。前面都带项目编号、项目名称、客户、业务几列。
- **项目档案**（`RegistersView.tsx`、新的 `RegisterTable.tsx`）：
  - 页签：「全部业务」（所有 4 栏行，包括硬件的额外项目）、每种有行的软件业务、每种有登记表或有项目用到的硬件业务。TV / 灯箱 / 弱电 / 光伏现在都有页签。
  - 硬件页签读登记表：按字段一列，有搜索和 PM / 客户 / 状态 / 年份筛选、就地改、新增记录、导入 CSV、下载模板、导出 CSV、PD / BD 增删列。数的是服务包份数。
  - 软件页签读 4 栏表，和 REQ-049 一样。
  - 「登记表管理」按钮（PD / BD）：每种业务一行，选格式、看有几个字段（硬件没有字段的标红「还没有字段，需要先建」）、点「编辑字段」直接改。
- **导入**：
  - 硬件页签按登记表字段导入，按项目名称对项目。有两个项目同名时那一行报错、整批不写入（不猜是哪一个）。
  - 软件页签和「全部业务」按 4 栏导入。REQ-049 去掉的「必须是内置业务」限制仍然去掉。
- **上线迁移**（`lib/mig053.ts` + `server/db.ts`，只跑一次，meta 记 `mig.req053.jobRecord`）：
  - 只看硬件业务的 4 栏行（按当时的分类）。软件的行、`pk.record` 一个都不动，迁移完自检一遍。
  - 删两类：
    - 049 拆出来、之后没人改过的：Service Item 是业务英文名，Detail 是登记表字段名（可以带「LED Display ② · 」这类前缀；LED 的旧名「Width 宽 (mm)」也认），Quantity / Special Notes 的值等于那一份 `pk.record` 现在的值（下拉比选项名）；

  - 其余的硬件行（上线后有人改过、新加的）原样留下，补上 `pk`，成为那一份的额外项目。有前缀的按前缀归到那一份，没有的归到第一份。报告里单独列一节给 PD 看。
  - 删掉的行原样存进项目的 `jobRecordLegacy053`，带原来的位置。
  - **先预演、再正式**：
    1. `scripts\req053-dryrun.bat`：在线复制一份库到 `data\migrations\053-dryrun-<时间>.db`，在副本上跑同一份规则，报告写到 `data\migrations\053-jobrecord-dryrun-<时间>.md`。正式库不动。正式迁移已经跑过时，它直接说明并退出，不出一份「0 行」的报告。

  - 没确认之前，启动时数一遍要删几行：有要删的就不迁移，日志里写一句原因；那些行先显示在登记表卡的「额外项目」里。没有要删的（新装的库、049 之前的老库）直接跑完记标记。
