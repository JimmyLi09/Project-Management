# 需求：售前接洽（Approach）——售前记录不占项目编号，转为正式项目时才编号

- **需求编号**：REQ-054
- **所属系统**：Project-Management（项目协作台 · 项目列表 / AV 方案成本 / 编号）
- **状态**：已实现（#104，2026-10-13；落地说明见 §4）
- **创建日期**：2026-10-12
- **优先级**：P1 · 1012 上线后反馈
- **来源**：
  - JM 1012：「投影属于售前，售前不要进项目编号，只是在 approach project stage，shall be independent one」；
  - 1012 选定：
    - 单独一个「售前接洽」列表；
    - 点「转为正式项目」时才给编号；
    - 转正式时可选「新建正式项目」或「并入已有项目」；
    - 现有的 049 去掉编号，变回售前记录；
  - 原型 `Audax_JobRecord与售前接洽_原型_v2.html` →「售前接洽 Approach」「上线迁移预览」。
- **关联**：
  - REQ-006（项目编号）；
  - REQ-043 / REQ-051（权限）；
  - REQ-050（清单合并）；
  - AV-016 ~ AV-020（AV 01 立项询价 ~ 07 报价）。

## 1. 现状（查代码确认）
- **AV 01 立项询价**（`app/api/av/inquiry/route.ts` POST）调用 `newProject()` + `insertProject()` 新建一个普通项目。新建时没给编号。
- **服务端启动时**的 `backfillSerials()`（`server/db.ts:150-170`）会给所有没编号的项目按创建顺序补编号。所以 AV 建的询价一重启就拿到了编号。
- 实际例子：
  - **049 · 147-Senja Close sales gallery**（只有投影，10/07 由总监 PD 从 AV 立项询价建）和已有的 **007 · 147-Senja Close sales gallery**（LED + 投影，Kian Lim 负责，已交接）重复了。
  - **046 · BOC Lobby LED** 也是从 AV 立项询价建的：没有负责人，交接未开始。是否一并去掉编号见 §2.7。
- 现在代码里的「售前」只是**算出来的阶段**（`projStage()`：没有负责人、排期没开始 → `presales`），不是一种单独的记录。编号、项目列表、总览、统计都照算。
- **AV 数据**按 `project_id + line` 存，表有：
  - `av_inquiry`（主键 project_id）；
  - `av_drawing`、`av_config`、`av_config_draft`、`av_config_draft_u`、`av_cost_sheet`；
  - `av_quote`、`av_judge`、`av_upload`（这三张没有 line，`av_extraction` 挂在 drawing 上）。
  - 也就是说，**同一个项目里同一条业务线只能有一套 AV 方案**。

## 2. 功能说明

### 2.1 新概念：售前记录（Approach）
- 项目对象新增：

  ```ts
  approach?: {
    status: 'open' | 'lost' | 'converted' | 'merged';
    source: 'av';                // 以后别的入口也能建,先只有 AV
    createdAt: number;
    convertedAt?: number; convertedBy?: string;
    mergedInto?: string;         // 并入的项目 id
    lostAt?: number; lostBy?: string; lostReason?: string;
    legacySerial?: number;       // 迁移时去掉的原编号(回退用)
  }
  ```

- `isApproach(p)` = `p.approach` 存在且 `status` 不是 `'converted'`。
- 状态含义：
  - `open`：在「售前接洽」列表；
  - `lost`（未成交）和 `merged`（已并入）：只读，在「已关闭」里；
  - `converted`（转为新正式项目）：从此就是普通正式项目。
- **售前记录没有编号**（`serial` 为空）：
  - `backfillSerials()` 必须跳过 `isApproach(p)`；
  - `nextProjectSerial()` 不受影响，仍取全库最大值 + 1。
- 显示：
  - 编号位置统一显示灰色标签「售前」（英文 Approach）；
  - `projLabel()` 对售前记录返回「售前 · 名称」。
- 和算出来的阶段 `presales` 是两回事：正式项目还没指派负责人时，照旧显示阶段「售前」，但它**有编号、在正式项目里**。界面文案用「售前接洽」区分，避免混淆。

### 2.2 入口：AV 立项询价建的是售前记录
- `POST /api/av/inquiry` 新建项目时写上 `approach = { status: 'open', source: 'av', createdAt }`，不给编号。
- 项目页的「新建项目」不变，仍然直接建正式项目、立刻编号。
- 「复制项目」复制出来的是正式项目（有编号）。复制售前记录也一样，复制品是正式项目。

### 2.3 售前记录在哪里出现、在哪里不出现
- **出现**：
  - 项目列表页新增标签：**正式项目 / 售前接洽 / 已关闭**，默认「正式项目」；
  - AV 工作台加同样的筛选（全部 / 售前接洽 / 正式项目），行上有「售前」标签；
  - 全局搜索（结果带「售前」标签）；
  - 通讯录（项目编号栏显示「售前」）。
- **不出现、不计数**：
  - 总览的项目数和各卡片；
  - 我的待办和侧栏数字；
  - 团队负载；
  - 统计报表、KPI、积分；
  - 收款看板、财务；
  - 向上汇报；
  - 项目档案（跨项目登记表页）。
- **建议实现**：在 `lib/project.ts` 加两个函数，替换各页面现在的 `projects.filter(...)` 入口，保证口径一致：
  - `formalProjects(list)`：正式项目，排除 `isApproach`；
  - `approachProjects(list, status?)`。
- 需要排查的地方，以实际代码为准：
  - `OverviewView`、`ProjectsView`、`MyTasksView` / `lib/myTasks.ts`、`App.tsx` 侧栏数字；
  - `TeamView`、`StatsView`、`KpiView` / `lib/kpi.ts`、`lib/metrics.ts`；
  - `FinanceView`、`DirectorUpdateView`、`RegistersView`、`ContactsView`；
  - `api/av/overview`。
- 售前记录可以正常走 AV 01 ~ 07：图纸、方案、成本、报价都能做。
- 售前记录**不能**指派 PM、不能提交交接、不能开 Invoice。这些位置显示「请先转为正式项目」，后端同样拒绝。

### 2.4 转为正式项目（Sales / PD / BD）
- 售前接洽列表和 AV 01 页顶部都有「**转为正式项目**」按钮。
  - 权限沿用 `canCreate`（Sales / PD / BD），后端校验。
  - AV 01 页顶部同时显示一行提示：「售前记录 · 未编号」。
- 弹窗二选一：

**① 新建正式项目**
- 这条记录本身变成正式项目：
  - `serial = nextProjectSerial()`；
  - `approach.status = 'converted'`，并记 `convertedAt` / `convertedBy`。
- 弹窗显示「将获得编号 0XX」。可以顺便填报价号和 PM（PM 选填）。
- AV 数据不用搬（project_id 不变）。
- 写日志「售前转为正式项目，编号 0XX」。

**② 并入已有项目**
- 下拉选已有的正式项目，同名的排在最前并标「同名，建议」。
- **按业务逐条处理**：
  - 目标项目**没有**这项业务：给目标项目新增一个服务包（`buildPackage` + REQ-050 的清单合并，和加业务一样）。
  - 目标项目**已有**这项业务：并入已有的那个服务包，不新增第二份。
- **AV 冲突检查**：如果目标项目这条业务线已经有自己的 AV 数据，这条业务**不能并入**，弹窗写明原因，建议改用「新建正式项目」。算「有 AV 数据」的情况：
  - `av_config`、`av_drawing`、`av_cost_sheet`、`av_config_draft(_u)` 中有这条线的记录；
  - 或者 `av_quote` 有任何记录。
  - 只有系统补建、内容为空的 `av_inquiry` 不算冲突。
- **搬什么**：
  - 售前记录的 AV 数据整体改挂到目标项目：`av_drawing` / `av_config` / `av_config_draft(_u)` / `av_cost_sheet` 按 line 搬，`av_judge` / `av_upload` / `av_quote` 全部搬，`UPDATE project_id`；
  - 联系人：目标没有的才加（按姓名 + 电话判重）。
- **立项记录合并**（`av_inquiry` 主键是 project_id，所以是合并、不是搬）：
  - lines 取并集；
  - 搬过去的线，规则包版本用售前那份的，因为方案是按它算的。和目标原来不同的写进日志；
  - 地点、补充说明和 answers：目标为空才补；冲突时以目标为准，售前的值写进日志；
  - 合并完删除售前那条 `av_inquiry`，原内容存进售前记录的 `approach.inquiryLegacy`。
- **冲突字段**（客户、交付日、报价号）：以目标项目为准，售前的值写进目标项目日志。
- 售前记录本身**不删除**：
  - `approach.status = 'merged'`、`mergedInto = 目标 id`，只读，留在「已关闭」里，点开显示「已并入 007 · …」并带链接；
  - 它自己的排期 / 清单模板行原样留着，不并过去（它们是新建时的模板，没人填过）。
- 两边都写日志：目标「并入售前记录 X（投影）」，售前「已并入 007」。
- **整个并入放在一个数据库事务里**，目标项目用 `saveProjectCAS` 防并发覆盖。任何一步失败就整体回滚。

> 说明：原型 v2 里「作为第二份（投影 ②）」这个选项**不做**。AV 数据按「项目 + 业务线」存，同一项目同一条线只能有一套方案；要做第二份需要先改 AV 的数据结构，另开需求。需要第二套方案时用「新建正式项目」。

### 2.5 未成交（Sales / PD / BD）
- 售前接洽列表每行有「未成交」：
  - 可以选填原因；
  - `approach.status = 'lost'`；
  - 移到「已关闭」，只读。
- 「已关闭」里可以「重新打开」，`status` 回到 `open`，写日志。
- **不删除任何数据**。

### 2.6 权限
- 查看：
  - 能看 AV 方案成本模块的人都能看售前接洽（REQ-051 权限表的「AV 方案成本」模块）；
  - REQ-043 照旧：PM / Engineer 只看自己是负责人的；售前记录没有负责人，所以他们看不到。
- 新建（AV 立项询价）、转为正式项目、未成交、重新打开：Sales / PD / BD，后端同样校验。
- 售前记录里的 AV 编辑权限和现在 AV 模块一致。

## 4. 落地说明

- **数据**：
  - 项目上多一个 `approach`（`lib/types.ts`）。字段和 §2.1 一样，另加：
    - `mergedAt` / `mergedBy`；
    - `reopenedAt` / `reopenedBy`；
    - `inquiryLegacy`：并入时被合并掉的那条 AV 立项记录，原样存这里。
  - 判断和筛选统一在 `lib/approach.ts`：
    - `isApproach`：有 `approach` 且不是 converted；
    - `isOpenApproach`、`isClosedApproach`：未成交 / 已并入算已关闭；
    - `formalProjects`、`approachProjects(list, status?)`。
  - **没有新表、新列。**
- **编号**：
  - 启动时的 `backfillSerials()` 跳过售前记录。这就是 049 出现的根因：以前 AV 建的项目一重启就被补上了号。
  - `nextProjectSerial()` 不变，仍是全库最大编号 + 1。
  - 编号位置统一显示灰色「售前」/ Approach。`projLabel()` 对售前记录返回「售前 · 名称」。
- **入口**：
  - `POST /api/av/inquiry` 新建时写上 `approach = { status: 'open', source: 'av', createdAt }`，不给编号。
  - 项目页「新建项目」、「复制项目」照旧建正式项目。复制售前记录，复制品也是正式项目，不带 `approach`。
- **列表和统计的口径**：在前端 store 这一层统一分开（`components/store.tsx`）。
  - `projects` 只有正式项目。总览、我的待办和侧栏数字、团队负载、统计报表、KPI、积分、收款看板、向上汇报、项目档案、登记表页、用户管理里的「名下工作」都从它来，所以都不算售前记录。
  - `allProjects` 连售前记录一起，只有这几处用：项目列表的三个标签、打开单个项目、通讯录、全局搜索。
  - `avProjects` 是正式项目加上还开着的售前记录，AV 各页的项目选择用它。已关闭的售前记录不进 AV。
  - 服务端几处也一样：
    - AV 工作台接口给每行带 `approach`，已关闭的不列；
    - 登记表导入按项目名 / 编号对项目时跳过售前记录。147-Senja Close 售前和正式的 007 同名，不这样会报「有不止一个项目叫…」。
- **在哪里出现**：
  - **项目列表**：标签「正式项目 / 售前接洽 / 已关闭」，默认「正式项目」，每个标签带个数。
    - 售前接洽一行：编号（「售前」；上线时去掉号的写「原 049，上线时去掉」）、名称、客户、业务、来源（AV 立项询价 · 日期 · 谁）、AV 进度（和工作台同一套阶段）。
    - 操作按钮：「AV 方案」「转为正式项目」「未成交」。
    - 已关闭一行：未成交 · 原因，或「已并入 007 · …」，带「打开并入的项目」「重新打开」。
  - **AV 工作台**：「全部 / 售前接洽 / 正式项目」筛选，行上标「售前」。
  - **AV 顶栏的项目下拉**：售前记录前面写「售前 ·」，正式项目前面写编号，同名的两条分得开。
  - **全局搜索**：正式项目列表下面另列「售前接洽里也有 N 条」，带「售前」标签。
  - **通讯录**：项目编号栏写「售前」；已并入的不列，联系人已经并到目标项目。
  - **项目页和 AV 01 页**：顶上一条「售前记录 · 未编号」，配「转为正式项目」按钮。已关闭的写「已并入 007 · …」（带链接）或「未成交 · 原因」+「重新打开」。
- **售前记录上不能做的**（按钮藏起来，`applyAction` 也拒绝，提示「请先转为正式项目」）：
  - 指派 PM / 工程师、转交；
  - 交接（发起、修改、接单）、完工、Sales 核对、变更；
  - 开 Invoice、财务字段、收款、收款风险；
  - 归档。

  项目页原来的售后流程卡片换成一句提示。AV 01–07 照常能做。
- **已关闭（未成交 / 已并入）只读**：
  - 项目动作一律拒绝；`canEdit` / `canMeta` 为假，界面没有编辑按钮；
  - AV 的写接口也拒绝：立项、方案、草稿、成本、报价、图纸上传 / 手填 / 重新解析 / 删除、判读、校核、设备建议；
  - 已并入的不再自动补建 AV 立项记录。
- **转为正式项目**（`POST /api/approach`，在 `server/approach.ts`；Sales / PD / BD）：
  - **① 新建**：这条记录本身拿下一个编号，`status = converted`，写日志「售前转为正式项目，编号 0XX」。
    - 可以顺便填报价号；PD / BD 还可以顺便指派 PM（Sales 本来就不能指派 PM）。
    - AV 数据不用搬。
  - **② 并入已有**：下拉里同名的排最前，标「同名，建议」，默认就选它；已归档的项目不能选。选好后先请求预览（`GET /api/approach?id=&target=`），弹窗逐条业务列出：
    - 已有 / 没有；
    - 怎么并：并入已有的那份服务包 / 新增一份（走现成的「加业务」，清单按 REQ-050 合并）；
    - 要搬几条 AV 数据；
    - 有没有冲突。
  - **冲突**：
    - 售前这条线有 AV 数据（方案 / 图纸 / 成本 / 草稿），目标这条线也有，就不能并。两边都有 AV 报价也不能并。
    - 任何一条冲突，**整条售前都不并**，提示改用「新建正式项目」，按钮灰掉，接口同样拒绝。
